프로브요약
01 DNS: 이름 → IPObservedexample.com 하나에 IP 넷이 돌아오고, localhost는 DNS에 묻지 않고 /etc/hosts에서 바로 IP로 바뀐다.Meaning이름은 IP만 정하고, 포트는 URL이 정한다.
02 curl: HTTP의 모양Observedcurl은 TCP 연결을 먼저 맺고 그 위로 요청 텍스트를 보내며, 없는 경로 /nothing도 연결은 같고 상태 줄만 404다.Meaning무엇을 돌려줄지 판단하는 쪽은 커널이 아니라 서버 프로그램이다.
03 telnet: HTTP를 손으로Observed빈 줄을 치기 전까지 서버는 다음 헤더를 기다리고, 깨진 요청에는 400이나 405를 돌려준다.Meaning요청의 끝은 빈 줄이고, 서버는 요청 줄의 문법, 헤더, 의미를 차례로 판단한다.
04 nc: 내가 서버ObservedContent-Length가 없으면 브라우저는 연결이 끊길 때까지 로딩하고, Content-Length: 5면 5바이트만 그린다.Meaning브라우저는 응답이 끝난 것을 Content-Length나 연결의 끝으로만 안다.
05 strace: 서버와 커널 사이Observed서버는 socket, bind, listen 다음 accept4에서 멈추고, 접속이 오면 listen 소켓 fd 3과 다른 연결 소켓 fd 4를 받는다.Meaninglisten 소켓은 새 연결만 받고, client와의 대화는 client마다 새로 생기는 연결 소켓으로 한다.

1. 앞 이야기와 용어

읽고 나서 만들기 대신 겪고 나서 만들기
관찰에서 생긴 질문을 팀 프로토타입으로

웹 서버 주차의 출발점을 책 대신 명령으로 정함. curl, telnet, nc, strace로 요청 하나를 직접 따라가고, 다음 트랙부터는 작은 C 코드를 손으로 따라 침. 각 프로브의 끝은 힌트 없이 혼자 하는 변경 과제 하나.

트랙겪어 볼 것기록
T1 CLI이름 → IP, HTTP의 모양, socket → bind → listen → accept이 페이지
T2 socket Cecho 서버 따라치기, 두 번째 client가 멈추는 이유한 번에 한 client만 받는 echo 서버
T3 TCPSO_REUSEADDR, TIME-WAIT, SIGPIPE서버 재시작과 응답 도중 떠난 client
T4 HTTP정적 GET, MIME, 404, keep-alive, 깨진 요청다음
T5 concurrencyfork, pthread, epoll을 wrk로 비교
T6 proxyReverse Proxy, 중계, C Forward Proxy
용어뜻
client서버에 연결하는 프로그램이 페이지에서는 curl, telnet, nc, 브라우저
DNS이름을 물으면 IP를 알려 주는 서버와 그 규칙
/etc/hosts이름과 IP를 직접 적어 둔 파일DNS보다 먼저 봄
요청 줄요청의 첫 줄: 메서드, 경로, 버전 (GET / HTTP/1.1)
상태 줄응답의 첫 줄: 버전, 상태 코드, 설명 (HTTP/1.1 200 OK)
빈 줄헤더가 끝났다는 표시
keep-alive응답 뒤에도 연결을 닫지 않고 다음 요청을 받는 방식
Content-Lengthbody가 몇 바이트인지 알리는 헤더
시스템콜프로그램이 커널에 일을 부탁하는 호출 (socket, bind, listen, accept, connect)
fd프로세스가 커널 안의 파일이나 소켓을 가리키는 번호
listen 소켓listen을 부른 소켓, 새 연결만 받음
연결 소켓accept가 client마다 새로 만든 소켓, 대화는 여기로

3. DNS: 이름 → IP (01)

이름이 IP로 바뀌는 곳은 두 군데
/etc/hosts가 먼저, 없으면 DNS 서버

상황
내 PC에서 example.com과 localhost의 IP를 여러 방법으로 조회
질문
이름은 어디서 IP로 바뀌고, 포트는 누가 정하나
ip -br addr                    # 내 PC의 인터페이스와 IP
getent ahosts example.com      # /etc/hosts 다음 DNS까지, OS 방식으로
dig A example.com +short       # DNS 서버에 직접: IPv4
dig AAAA example.com +short    # IPv6
cat /etc/hosts /etc/resolv.conf
본 것
① example.com 하나 → IP 넷② localhost는 DNS 없이 /etc/hosts에서 바뀜③ 포트는 DNS 답에 없음, URL이 정함
웹 서버에서
서버 코드가 이름을 찾을 때 쓰는 getaddrinfo()는 getent와 같은 순서로 찾음
더 보기
내 PC로 살펴보는 IP와 Host

4. curl: HTTP의 모양 (02)

연결이 먼저, 요청 텍스트는 그 위로
무엇을 돌려줄지는 서버 프로그램이 정함

상황
curl을 -v로 실행해 연결 과정과 헤더를 봄
질문
HTTP 요청과 응답은 어떤 모양이고, 없는 경로는 어디서 걸러지나
curl -sv http://example.com/ -o /dev/null 2>&1 | bat -l http
curl -sv http://example.com/nothing -o /dev/null 2>&1 | bat -l http
curl -sv http://localhost/ -o /dev/null 2>&1 | bat -l http
# -v = 연결 과정과 헤더를 stderr로, -o /dev/null = body 버림, 2>&1 = 둘을 합쳐 bat으로
본 것
① * 줄 = curl의 기록, > 줄 = 보낸 것, < 줄 = 받은 것, { 줄 = 받은 body 크기② 내 쪽 포트는 실행마다 바뀜 (커널이 고른 임시 포트)③ /nothing도 연결은 같고 상태 줄만 404
이유
커널은 연결만 맺음, 경로를 읽고 상태 코드를 고르는 것은 서버 프로그램
웹 서버에서
404 판단은 내 서버 코드가 할 일

5. telnet: HTTP를 손으로 (03)

요청의 끝은 빈 줄
깨진 요청은 읽는 단계마다 다른 때에 걸러짐

상황
curl이 대신 쳐 주던 요청 텍스트를 telnet으로 직접 입력, nginx(localhost:80)에 보냄
질문
서버는 요청이 끝난 것을 어떻게 알고, 깨진 요청에는 무엇을 돌려주나
telnet localhost 80
# 연결되면 직접 치고 Enter 두 번
GET / HTTP/1.1
Host: localhost

nc localhost 80                # 줄 끝 \n만 (nc -C면 \r\n)
본 것
① 빈 줄 전까지 서버는 다음 헤더를 기다림② HTTP/1.0은 응답 뒤 연결이 닫히고, HTTP/1.1은 유지 (keep-alive)③ telnet은 HTTP를 모름, 받은 바이트를 그대로 보여 줌
바꾼 요청응답과 연결판단 시점
요청 줄 앞 공백, HTTP1.1400close요청 줄을 읽자마자 (문법)
HTTP/1.1에서 Host 없음400close헤더를 다 읽은 뒤
메서드 GOT405keep-alive문법 통과 후 (의미)
줄 끝 \n만200keep-alive받아 줌읽을 때 너그럽게, 쓸 때 엄격하게
웹 서버에서
내 서버의 파서도 빈 줄을 만날 때까지 읽어야 함문법 오류는 400, 모르는 메서드는 405로 나눠 답함

6. nc: 내가 서버 (04)

역할 바꾸기: 브라우저가 client, 내가 서버
브라우저는 응답의 끝을 Content-Length나 연결의 끝으로 앎

상황
nc -l 8080을 띄우고 Windows 브라우저로 접속, 찍힌 요청에 응답을 손으로 침
질문
브라우저는 무엇을 보내고, 무엇을 믿고 화면을 그리나
nc -l 8080
# Windows 브라우저에서 http://localhost:8080/hello → 요청이 찍히면 직접 응답
HTTP/1.0 200 OK
Content-Type: text/html

<h1>hello from nc</h1>
본 것
① 브라우저 요청은 curl보다 헤더가 훨씬 많음 (언어, 압축, prefetch)② 친 줄마다 바로 렌더링③ Content-Length가 없으면 연결이 끊길 때까지 로딩④ Content-Length: 5면 5바이트만 받아 <h1>H만 그림⑤ 경로는 nc가 읽지 않음 → 어느 경로든 같은 화면⑥ nc -l은 한 번만 받음 → 새로고침하면 연결 거부 (서버 커널이 RST를 돌려보냄)
웹 서버에서
응답마다 Content-Length를 정확히 넣어야 keep-alive 연결에서 다음 응답과 섞이지 않음한 번 받고 끝나는 서버는 서버가 아님 → accept를 반복하는 구조 (T2)

7. strace: 서버와 커널 사이 (05)

서버는 socket → bind → listen 다음 accept4에서 멈춤
접속이 오면 새 fd

상황
strace를 붙인 nc -l 8080에 다른 터미널의 nc로 접속, curl도 strace로 봄
질문
서버와 client는 커널에 무엇을 어떤 순서로 부탁하나
strace -f -e trace=network nc -l 8080        # 터미널 1
nc localhost 8080                            # 터미널 2
ss -tanp 'sport = :8080'                     # 터미널 3
strace -f -e trace=network curl -s http://example.com/ -o /dev/null
본 것
① 서버는 accept4에서 잠들었다가 접속이 오자 깨어남② listen 소켓은 fd 3, 연결 소켓은 fd 4③ curl은 DNS(:53) → connect(:80) → 요청 텍스트를 sendto
이유
fd 3은 다음 client를 받으려고 남아 있고, 대화는 accept가 만든 fd 4로 함
웹 서버에서
내 서버 코드도 같은 순서로 부름 → T2에서 C로 직접
