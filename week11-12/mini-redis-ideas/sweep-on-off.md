# [CJG] 만료된 key를 주기적으로 청소할 때와 청소하지 않을 때의 time & memory 차이 비교

## 관찰 대상

[CJG] 만료된 key에 대한 주기적인 청소가 메모리를 아끼는 대신 GET 응답 시간을 얼마나 내주는지의 비율을 봅니다. 

주기적인 청소가 필요없는 케이스가 있는 지 찾아봅니다.

time 쪽은 004 기록에 근거가 있지만, 청소가 없을 때 memory가 얼마나 쌓이는지는 잰 적이 없어요.

## 예상

[CJG] 주기적인 청소를 하지 않았을 때 생기는 memory 낭비의 비용이 더 클 것 같습니다.

## 현재 상태와 실험군

| | 현재 상태 | 실험군 |
|---|---|---|
| 동작 | 25 ms마다 만료된 key를 최대 2,000개까지 지워요 | 만료된 key를 지우지 않아요 |

## 측정 방법

측정하지 않기로 했어요. 아래는 측정하지 않기로 정하기 전까지 계획한 방법이에요. 반복은 3회, value는 `bench.py`의 `VALUE`(100바이트)로 정했고, 실험 브랜치에서 시나리오를 커밋한 뒤에 잴 계획이었어요.

실험군은 `SERVER_FLAGS='-DSWEEP_MAX_COUNT=0'`으로 빌드해요. 그러면 `store_delete_expired`의 `while`이 한 번도 돌지 않으므로, 코드를 고치지 않고도 청소를 끌 수 있어요.

보관 기간이 없는 key 150,000개를 미리 채우고, 60초 동안 1 ms마다 `TTL: 2`인 새 key를 저장하면서 미리 채운 key에 작은 GET을 초당 5,000개 보내요. GET 지연은 `bench.py`의 열린 루프로 재고, memory는 1초마다 서버의 `/proc/<pid>/status`에서 `VmRSS`를 읽어 늘어나는 기울기를 비교해요.

미리 채운 150,000개는 버킷을 65,536개로 늘려 두기 위한 값이에요. 실험군이 60초 동안 쌓아도 210,000개라서 버킷을 늘리는 경계(262,144) 아래에 머물므로, 측정 길이를 바꾸면 이 값도 다시 계산해요. 기록은 실험 브랜치 `CJG-sweep-ab`의 `docs/measurements/server/006-CJG-sweep-ab.md`에 남길 계획이었어요.

## 결과

측정하지 않고 추론으로 닫았어요. 청소를 끄면 다시 저장되지도 지워지지도 않는 만료 key가 끝없이 쌓이고, 그 속도는 계산으로 나와요. 청소를 꺼서 아끼는 비용은 거의 없어요.

memory 쪽은 entry 하나의 크기로 계산해요. `struct entry`는 64바이트이고, key 약 12바이트와 value 100바이트를 더하면 약 176바이트예요. glibc가 할당을 16바이트 단위로 올리고 heap 배열의 포인터 8바이트가 더해지므로, entry 하나는 약 200바이트를 차지해요. 만료가 초당 1,000개이면 청소가 없을 때 1초에 약 200 KB, 1분에 약 12 MB, 1시간에 약 720 MB가 쌓여서, 이 머신(15 GiB)의 memory는 하루 안에 다 차요. `VmRSS` 기울기를 재는 일은 이 계산을 확인하는 일일 뿐이에요.

time 쪽에서 청소의 비용은 검사와 지우기로 나뉘어요. 검사는 25 ms마다, 즉 초당 40번 heap의 맨 앞 entry 하나의 만료 시각을 지금 시각과 비교하는 일이라서, 만료된 key가 없으면 if문 한 번으로 끝나요. 지우기는 청소를 꺼도 사라지지 않아요. 다시 저장되는 key라면 PUT이 `store_set`의 `hash_replace`로 만료된 옛 entry를 빼고 `entry_discard`로 지우므로, 지우는 일이 청소에서 PUT으로 자리만 옮겨요.

"청소가 필요 없는 케이스"는 만료되는 모든 key가 결국 PUT으로 덮이거나 DELETE로 지워질 때뿐이에요. 예를 들어 정해진 key 몇 개만 계속 갱신하는 client가 그래요. 이 경우는 두 갈래로 나뉘어요.

- 만료되는 key가 없으면, 청소는 시각을 비교하는 if문 하나를 주기적으로 돌릴 뿐이므로 꺼서 아끼는 오버헤드가 의미 없어요.
- 정해진 key만 쓰지만 만료가 생기면, 청소가 지우던 entry를 PUT이 대신 지우므로 꺼도 지우는 일이 줄지 않아요. 만료된 entry는 다음 PUT까지 남지만, key 수가 정해져 있으므로 낭비량도 그 key 수 × 약 200바이트로 막혀 있어요.

그리고 서버는 자기 client가 이런 client인지 미리 알 수 없어요. 청소를 껐는데 한 번 쓰고 버리는 key가 하나라도 섞이면 memory가 끝없이 늘어나요. 우리 상품 데모의 이전 목록 세대가 그런 key예요. 얻는 것은 초당 비교 40번 정도이고 잃을 수 있는 것은 memory 전체이므로, 청소를 끄는 선택지는 운영자에게 쓸모가 없어요. 잴 가치가 남은 질문은 청소를 할지가 아니라 청소 주기를 얼마로 잡을지예요.
