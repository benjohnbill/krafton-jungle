crawler 트래픽과 서버의 방어

crawler가 서버에 떠넘기는 부하와 대역폭, 1993년부터 2026년까지
서버가 쌓은 layer 여섯 개와 crawler가 그것을 넘는 방식, 우리 Reverse Proxy에 넣을 자리

이 페이지는 Claude(Anthropic의 AI)가 리서치 파일 세 개만 보고 썼어요. 숫자와 날짜마다 출처 링크와 등급을 붙였어요. primary는 당사자의 원문을 읽은 것, secondary는 보도나 요약만 읽은 것, unverified는 확인하지 못한 것이고, unverified인 문장은 회색으로 적었어요. 누군가를 비판하는 주장에는 같은 모양의 칸에 그 상대의 응답을 붙였고, 기록된 응답이 없으면 "응답 기록 없음"이라고 적었어요.

가운데 칸을 누르면 3장의 카드로 가요. layer마다 crawler는 그 질문에 맞는 속성을 갖춰 넘어오고, 어느 layer도 crawler를 멈추지 못해요. 그래서 마지막 layer는 "누구이고, 누가 값을 내는가"를 물어요. 이 정리는 리서치 파일의 해석이에요.

crawl-to-refer ratio: 크롤링 몇 번에 방문자 한 명

검색 엔진과 사이트 사이의 옛 거래는 "크롤링하게 해 주면 독자를 보내 줄게"였어요. crawl-to-refer ratio는 그 거래가 얼마나 지켜지는지 재는 숫자예요. 한 회사의 crawler가 가져간 HTML 요청 수를, 그 회사를 Referer header에 적고 들어온 방문 수로 나눠요. primary

방어와 우회의 11 라운드

방어 하나가 client의 속성 하나를 시험하면, crawler는 그 속성을 갖춰 답해요. 리서치 파일의 escalation 표를 그대로 그렸어요.

라운드별 출처
  1. 1 robots.txt → 무시, 이름 숨김. robots.txt는 부탁이에요. "These rules are not a form of access authorization." primary SourceHut이 본 crawler는 robots.txt를 무시했어요. primary
  2. 2 User-Agent 차단 → browser UA 흉내. "random User-Agents that overlap with end-users" primary
  3. 3 JA3 fingerprint → handshake 복제. curl-impersonate 계열은 browser와 같은 handshake를 보내요. primary 2023년 Chrome의 extension 섞기도 JA3를 깼어요. primary
  4. 4 IP rate limit, 차단 → IP 회전. Bidder's Edge: "We eventually adopted the rotating proxy servers." primary Read the Docs: "from many IP addresses" primary
  5. 5 datacenter IP 평판 → residential proxy. "mostly residential, in unrelated subnets" primary IP의 출처는 rate limit 카드의 접힌 칸에 있어요.
  6. 6 TLS, HTTP/2 검사 → 진짜 browser 실행. Chrome의 새 headless는 보통 Chrome과 같은 코드를 돌려요. 그래서 바이트가 진짜예요. primary
  7. 7 JS challenge, PoW → headless가 풀이. 기본 난이도의 Anubis 답은 C 풀이기로 약 0.017초예요. primary Codeberg: "the AI crawlers learned how to solve the Anubis challenges" secondary
  8. 8 headless 속성 검사 → stealth plugin. stealth plugin이 headless와 보통 Chrome의 차이를 하나씩 고쳐요. secondary
  9. 9 CDP 신호 탐지 → 신호 회피, V8 수정. 2024년 탐지 쪽이 자동화 통로(CDP)의 흔적을 찾았어요. secondary 2025년 5월 V8 commit 두 개가 그 흔적을 없앴어요. primary
  10. 10 그림 CAPTCHA → 풀이 서비스, ML. 풀이 서비스 공개 가격은 1,000건에 약 1 ~ 3달러예요. primary ETH Zurich의 모델은 reCAPTCHAv2 그림 문제를 100% 풀었어요. secondary
  11. 11 Turnstile, v3 점수 → token 구매. 같은 서비스가 Turnstile token도 1,000건에 1.45달러에 팔아요. primary

① 1993 ~ 1994: 초당 요청 1개와 robots.txt

1993년 9월, Martijn Koster는 회사 전용선에 붙은 Sun 4/330 한 대에서 Perl로 쓴 web server(Plexus)를 돌렸어요. 서버가 그에게 보고서를 메일로 보냈어요. 서로 링크된 같은 문서 묶음이 세 번이나 "in the order of 1 document per second"로 요청됐다는 내용이었어요. primary 지금 기준으로는 아주 작은 양이에요.

1994년 2월 25일 Koster는 www-talk에 표준을 제안했어요. primary

"Robots are one of the few aspects of the web that cause operational problems and cause people grief."

파일의 첫 이름은 /RobotsNotWanted.txt였어요. DOS의 8.3 파일 이름에 들어가지 않아서 1994년 6월 메일링 리스트에서 후보 7개를 놓고 투표했어요. Roy Fielding(나중에 HTTP/1.1 명세를 함께 쓴 사람)은 /spiders.txt를 냈고, 6월 17일 robots.txt로 정해졌어요. 6월 21일 Python을 만든 Guido van Rossum이 parser norobots.py를 올렸어요. primary Fielding의 MOMspider는 이 파일을 사이트마다 기한을 두고 cache했어요. 요청마다 파일을 다시 읽으면 서버 부하가 더 커지기 때문이에요. primary

6월 30일 합의된 이 문서는 IETF 표준(RFC 9309)이 되기까지 28년 동안 비공식 표준으로 남았어요. primary

② 1999 ~ 2000: eBay와 rotating proxy

1999년 11월 말까지 eBay는 경매 모음 사이트 Bidder's Edge가 쓴다고 본 IP 169개를 막았어요. Bidder's Edge는 proxy를 거쳐 계속 크롤링했어요. primary

주장eBay: Bidder's Edge가 요청의 최대 1.53%, 전송 데이터의 최대 1.10%를 차지했어요(1999년 10 ~ 11월). primary

응답Bidder's Edge: 하루 80,000 ~ 100,000 요청을 인정하고, 요청의 최대 1.11%, 데이터의 0.70%라고 주장했어요. 공동 창업자는 "We eventually adopted the rotating proxy servers."라고 진술했어요. primary

2000년 5월 24일 법원은 eBay에 가처분을 내줬어요. 부하는 작았지만, Bidder's Edge가 마음대로 크롤링하면 다른 회사도 따라 할 것이고 그 합이 eBay를 해칠 수 있다는 논리였어요. 같은 판결문에 따르면 eBay 사용자는 하루 약 1,000만 번 검색했어요. primary

26년 뒤 SourceHut이 같은 장면을 더 큰 규모로 적었어요: crawler가 "tens of thousands of IP addresses", "mostly residential, in unrelated subnets"에서 왔다고요. primary IP로 막는 방법은 1999년부터 같은 방식으로 뚫리고 있어요.

③ 2006: 이름 대신 DNS로 신원 확인

2006년 9월 20일 Google은 "any spammer could name their bot 'Googlebot'"이라고 적고, 사이트가 reverse DNS로 Googlebot을 확인하는 방법을 공개했어요. client IP의 이름을 조회해 googlebot.com으로 끝나는지 보고, 그 이름을 다시 조회해 같은 IP가 나오는지 봐요. primary

2021년 11월 Google은 IP 범위 JSON 파일을 두 번째 방법으로 더했어요. secondary 2024년 2월 HTTP 요청에 서명하는 표준 RFC 9421이 나왔어요. primary 그 위에 bot이 요청마다 서명하는 Web Bot Auth가 만들어지고 있어요. IETF webbotauth 그룹은 2025년 6월 15일 BOF로 시작해 2025년 10월 23일 정식 그룹이 됐고, 아직 RFC는 없어요. primary

신원을 묻는 방법은 이름(User-Agent)에서 네트워크(IP와 DNS)로, 다시 암호 서명으로 옮겨 가고 있어요.

④ 2024: 73 TB 청구서와 robots.txt 한 줄

4. 요청 하나 따라가기

가상의 서버 하나, crawler 넷
한 칸 오를 때마다 browser에 가까워짐

가상의 서버는 아래 다섯 검사를 이 순서로 해요. 네 crawler는 모두 robots.txt를 따르지 않아요. layer 1은 부탁이라서 막지 못해요. 검사 규칙은 설명을 위해 정한 가상의 설정이에요.

  1. 검사 1. IP 블록리스트 (layer 3, accept 직후)

    A curl ✓ 통과 블록리스트에 없는 새 datacenter IP예요. B User-Agent만 Chrome ✓ 통과 블록리스트에 없는 새 datacenter IP예요. C 같은 handshake ✓ 통과 블록리스트에 없는 새 datacenter IP예요. D headless browser ✓ 통과 residential proxy를 거친 집 IP예요.

  2. 검사 2. User-Agent 표 (layer 2)

    A curl ✗ 403 User-Agent가 자기 도구 이름을 그대로 말해요. 가상의 표는 browser가 아니라고 밝힌 User-Agent를 막아요. B User-Agent만 Chrome ✓ 통과 User-Agent가 Chrome이라고 말해요. C 같은 handshake ✓ 통과 User-Agent가 Chrome이라고 말해요. D headless browser ✓ 통과 진짜 Chrome의 User-Agent예요.

  3. 검사 3. JA4와 User-Agent 비교 (layer 2, TLS가 필요)

    A curl 검사 2에서 멈췄어요. B User-Agent만 Chrome ✗ 403 User-Agent는 Chrome인데 JA4는 다른 TLS 라이브러리를 가리켜요. 말과 바이트가 어긋나요. C 같은 handshake ✓ 통과 browser의 TLS 라이브러리로 만든 handshake라 JA4도 Chrome이에요. D headless browser ✓ 통과 진짜 Chrome이 보낸 바이트예요.

  4. 검사 4. IP 평판과 rate limit (layer 3)

    A curl 검사 2에서 멈췄어요. B User-Agent만 Chrome 검사 3에서 멈췄어요. C 같은 handshake ✗ 429 datacenter IP 하나에서 요청이 몰려요. datacenter 평판과 IP당 한도에 둘 다 걸려요. D headless browser ✓ 통과 집 IP 수만 개에 나눠서 IP마다 요청이 몇 개뿐이에요.

  5. 검사 5. proof of work (layer 4)

    A curl 검사 2에서 멈췄어요. B User-Agent만 Chrome 검사 3에서 멈췄어요. C 같은 handshake 검사 4에서 멈췄어요. JavaScript가 없어서 여기 왔더라도 막혔을 거예요. D headless browser ✓ 통과, 200 JavaScript를 실행해 challenge를 풀어요. 비용은 작아요. 다섯 layer를 모두 넘었고, 그래서 layer 5가 생겼어요: 이 crawler에게는 "bot인가"가 아니라 "누구이고, 누가 값을 내는가"를 물어야 해요.

Concurrency model마다 다른 비용

같은 방어도 Concurrency model에 따라 값이 달라요. iter에서는 main loop가 유일한 Worker라서, Worker 하나가 멈추면 서버 전체가 멈춰요. epoll에는 Worker가 없고, 루프 하나가 모든 연결을 돌려요.
