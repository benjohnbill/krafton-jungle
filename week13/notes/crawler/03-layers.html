crawler 방어 layer와 우회 방식

layer마다 client에게 질문 하나
방법마다: 보는 것, 쓰는 곳, 사람이 치르는 값, 뚫리는 방식, 우리 서버

주제요약
방어 layer 여섯 개Observedlayer 0부터 layer 5까지 방법 14개가 있고, layer마다 client에게 질문 하나를 한다.Meaning방법마다 뚫리는 방식이 있다: User-Agent는 browser의 문자열로, IP는 residential proxy로, proof of work는 headless browser로 넘는다.
우리 서버 (CJG)Observedrproxy에는 응답 cache가 있고, User-Agent 차단, TLS fingerprint, rate limit, tarpit은 만드는 중이다.MeaningCAPTCHA와 pay per crawl은 서버 혼자서는 만들 수 없다.
요청 하나 따라가기Observed가상의 서버에서 curl은 검사 2, User-Agent만 Chrome은 검사 3, 같은 handshake는 검사 4에서 멈춘다.Meaningheadless browser는 다섯 검사를 모두 넘으므로, 이 crawler에게는 누구이고 누가 값을 내는가를 물어야 한다.

출처 칩(primary, secondary, unverified)의 뜻은 한눈에 보기에 있다.

뚫리는 방식은 생각의 수준까지만 적었다. 특정 방어를 넘는 절차나 코드는 적지 않았다.

우리 서버 칸은 mini-webserver CJG 브랜치의 Reverse Proxy rproxy를 기준으로 적었다. rproxy는 Origin 앞에서 따로 도는 프로세스이고, TLS는 OpenSSL로 받는다. CJG에 있음은 지금 코드에 있는 것, 만드는 중은 테스트와 빈 자리는 있고 판단 코드를 아직 쓰는 중인 것, 가능은 OpenSSL이 들어와 만들 수 있게 됐지만 아직 없는 것, 계획, 아직 없음은 아직 만들지 않은 것, 못 함은 서버 혼자서는 만들 수 없는 것이다.

layer 0: 비용 줄이기

거절하지 않고 요청 하나의 값을 낮추는 layer다. client에게 묻는 것이 없다.

layer 2: 신원 묻기

"너는 누구인가"를 묻는 layer다. client의 말(User-Agent)과 client의 바이트(TLS, 네트워크)를 맞춰 본다.

User-Agent 차단

보는 것User-Agent 문자열뚫리는 방식browser의 문자열을 보내면 끝난다.우리 서버만드는 중 User-Agent는 Verdict로 간다. 표는 아직 없다.

자세히: 사례와 출처
보는 것
User-Agent header 문자열
쓰는 곳
ai.robots.txt가 nginx, HAProxy, Caddy용 설정 조각을 함께 준다. primaryKDE는 bot이 내세운 특정 MS Edge 버전 하나를 막았다. secondary
사람이 치르는 값
보통은 없다. 막은 문자열이 진짜 browser의 것이면 그 browser를 쓰는 사람도 막힌다(KDE의 Edge 차단).
뚫리는 방식
User-Agent는 client가 마음대로 쓰는 문자열이라, crawler가 흔한 browser의 문자열을 보내면 끝난다. SourceHut은 "random User-Agents that overlap with end-users"를 봤다. primary Cloudflare: "user agent headers alone are easily spoofed" primary 이름을 숨긴 crawler의 사례는 ⑤의 칸에 있다.
우리 서버
만드는 중 rproxy는 parse한 User-Agent를 Verdict의 입력으로 넘기고, Origin에도 그대로 보낸다. 그 값을 표와 비교해 403을 고르는 verdict_decide()는 아직 모든 요청을 통과시키는 빈 자리다. 싸고, 속이면 바로 뚫린다.

TLS fingerprint: JA3에서 JA4로

보는 것TLS handshake의 첫 메시지 ClientHello뚫리는 방식browser의 TLS 라이브러리로 같은 handshake를 보낸다.우리 서버만드는 중 TLS는 OpenSSL로 받고, ClientHello parser는 있다. JA4 계산은 쓰는 중이다.

자세히: 사례와 출처
보는 것
TLS handshake의 첫 메시지 ClientHello. 각 TLS 라이브러리(Chrome의 BoringSSL, Firefox의 NSS, OpenSSL, Python의 ssl)는 자기 모양을 만든다. 그래서 TLS fingerprint는 사람이 아니라 소프트웨어를 가리킨다. primary
판단
JA3(Salesforce, 2017)는 다섯 필드를 받은 순서대로 이어 MD5로 hash한다. primary2023년 초 Chrome이 연결마다 extension 순서를 섞기 시작하자, Fastly는 Chrome 연결마다 "practically a unique JA3 fingerprint"가 생긴다고 봤다. browser의 개인정보 보호 변경이었지 scraper 도구가 아니었다. primaryJA4(FoxIO)는 정렬한 뒤 hash해서 순서를 섞어도 값이 같다. a_b_c 모양이라 한 부분만 맞춰 볼 수도 있다. primaryHTTP/2에도 같은 생각이 있다. Akamai는 2017년 SETTINGS 값과 pseudo-header 순서로 만든 fingerprint를 발표하며 "detecting browser impersonators"를 용도로 들었다. primary
쓰는 곳
Cloudflare(JA4 Signals, 2024-08-12) primary, Stack Overflow(IP가 달라도 bot을 한 무리로 묶으려고) primary
사람이 치르는 값
직접은 없다. 드문 browser나 개인정보 보호 도구가 bot과 같은 fingerprint를 가질 수 있다.
뚫리는 방식
browser의 TLS 라이브러리로 다시 빌드한 HTTP client는 browser와 똑같은 handshake를 보낸다(curl-impersonate 계열). primary 진짜 headless browser도 진짜 fingerprint를 낸다. Cloudflare도 fingerprint는 "can be easily spoofed"라고 적었다. primary
우리 서버
만드는 중 rproxy가 TLS를 직접 받는다. TLS 라이브러리는 OpenSSL로 정했다(2026-11-24 결정). handshake 전에 recv(..., MSG_PEEK)로 평문 ClientHello를 엿보고, client_hello_parse()가 cipher와 extension을 wire 순서 그대로 읽는다. 이 parser는 openssl s_client와 curl이 보낸 바이트로 테스트한다. 그 값으로 JA4 문자열을 만드는 ja4_format()은 아직 빈 자리라서, 지금은 X-JA4 header가 빈 값으로 Origin에 간다.

layer 3: 양 제한하기

"얼마나 많이 오는가"를 묻는 layer다. 대부분 IP 주소를 열쇠로 센다.

IP, subnet, ASN, 국가 차단

보는 것출발지 IP와 그 네트워크뚫리는 방식IP를 계속 바꾼다.우리 서버계획, 아직 없음 accept() 직후 CIDR 표와 비교하고 닫는다.

자세히: 사례와 출처

위 숫자는 설명을 위한 계산이다. 실제로 SourceHut은 IP 하나에 요청이 약 1개씩 오는 트래픽을 봤다. primary

뚫리는 방식
residential proxy: 집과 휴대폰 회선의 IP를 빌려 요청을 내보내는 유료 네트워크다. 집 IP는 사람의 평판을 가진다.Read the Docs: 요청이 "from many IP addresses"로 와서 IP 단위 rate limit이 효과가 없었다. primarydiaspora*: IP 약 130만 개, IP당 2개 남짓 primary한도의 열쇠를 등록해야 얻는 것(OAuth client, 계정)으로 바꾸면 훨씬 잘 듣는다. Wikimedia가 client를 인증 쪽으로 옮기는 이유다. primary

residential proxy의 IP는 어디서 오나

Google Threat Intelligence Group(2026-01-29)은 IPIDEA 네트워크를 분석했다. proxy SDK가 앱 안에 들어가고, 앱을 깐 기기가 그 앱의 원래 기능과 함께 proxy의 출구가 된다. 개발자는 보통 다운로드 수만큼 돈을 받았고, 분석한 앱 상당수는 기기를 등록한다는 사실을 알리지 않았다. Android 앱 600개 넘게, Windows 파일 hash 3,075개가 나왔고, 2026년 1월 7일 동안 추적 중인 위협 그룹 550개 넘게 이 출구를 썼다. primary

2019년 IEEE S&P 논문은 residential proxy IP를 230개 넘는 나라에서 약 600만 개로 셌다. secondary

반론도 있다. 2026년 8월 GCC 메일링 리스트의 한 참여자는, AI scraper가 residential IP를 산다는 Sourceware의 주장이 자체 데이터로 보인 것이 아니라 외부 단서에서 나온 가설이며, 자원 사용량 수치도 공개되지 않았다고 지적했다. 그리고 차단의 강도를 증거에 맞추자고 했다. primary

행동 카운터와 honeypot

보는 것새 URL 속도, 4xx 비율, 함정 URL 요청뚫리는 방식IP를 흩거나 숨은 링크를 건너뛴다.우리 서버계획, 아직 없음 아무 페이지도 링크하지 않는 Route 하나를 함정으로 둔다.

여전히 IP 단위라 IP를 흩으면 같이 뚫린다. 페이지를 그려 보고 보이지 않는 링크를 건너뛰거나, sitemap의 링크만 따라가는 crawler에게는 honeypot이 닿지 않는다.
우리 서버
계획, 아직 없음 아무 페이지도 링크하지 않고 robots.txt가 막은 Route 하나를 두고, 요청한 IP를 일정 시간 막는다. Verdict가 요청 target을 입력으로 받으니, 그 Route는 Verdict의 표에 들어간다. IP마다 새 URL 속도와 4xx 비율을 세면 로그를 읽지 않는 fail2ban이 된다.

layer 4: 시험하기

"진짜 browser이고, 값을 치를 것인가"를 묻는 layer다.

proof of work (Anubis)

보는 것CPU를 쓴 증거, JavaScript와 cookie뚫리는 방식headless browser가 푼다. 비용은 작다.우리 서버가능, Route별로만 OpenSSL에 SHA-256이 있다. curl, ab, wrk, hey는 통과하지 못한다.

자세히: 사례와 출처
보는 것
client가 CPU를 썼다는 증거, 그리고 JavaScript를 실행하고 cookie를 지킬 수 있는가. 기본 설정은 User-Agent에 "Mozilla"가 들어간 요청만 시험한다. primary
쓰는 곳
SourceHut, GNOME(2026년 3월까지), KDE, Codeberg, FFmpeg, UNESCO. 2025년 7월까지 다운로드 약 20만 회 secondary
사람이 치르는 값
JavaScript나 cookie가 없는 사람, 텍스트 browser, 오래된 기기는 못 들어온다. 만든 사람도 "a tradeoff that I am not happy about"라고 적었다. primary검색 엔진이 보호된 페이지를 색인하지 못한다.GNOME에서는 링크가 퍼졌을 때 사람이 challenge 앞에서 최대 약 2분을 기다렸다. secondary
뚫리는 방식
headless browser는 스크립트를 실행하고 일을 한다. CPU 비용 자체는 작다. Tavis Ormandy의 C 풀이기는 기본 난이도의 답을 약 0.017초에 찾았다. primaryCodeberg(2025-08): "the AI crawlers learned how to solve the Anubis challenges" secondary이 방법이 실제로 거르는 것은 CPU가 아니라, 진짜 JavaScript 엔진과 cookie를 갖추라는 요구다.
우리 서버
가능, Route별로만 OpenSSL이 들어와서 SHA-256과 HMAC은 쓸 수 있다. 남은 문제는 client가 JavaScript를 돌려야 한다는 점이다. Verification client인 curl, ab, wrk, hey는 모두 통과하지 못한다. 그래서 기본은 끄고, 기능 테스트와 부하 테스트가 쓰지 않는 Route에만 걸 수 있다.

CAPTCHA와 보이지 않는 시험

보는 것퍼즐의 답, 또는 보이지 않는 점수뚫리는 방식풀이 서비스와 ML이 푼다.우리 서버못 함 외부 vendor의 서비스가 있어야 한다.

자세히: 사례와 출처
보는 것
reCAPTCHA v3: 동작마다 0.0 ~ 1.0 점수, 권장 기준 0.5, 사람을 멈춰 세우지 않음 primaryCloudflare Turnstile(2023-09-29 정식): browser API 검사와 작은 proof of work, 그림 퍼즐 없음 primary
사람이 치르는 값
사람의 약 15%가 CAPTCHA 퍼즐 앞에서 포기한다(Cloudflare). primary사람은 그림 CAPTCHA를 약 18초(실제 작업 중에는 22초)에 50 ~ 85% 정확도로 푼다(USENIX Security 2023, 참가자 1,400명). primaryreCAPTCHA v2에 사람이 쓴 시간은 13년 넘게 약 8억 1,900만 시간이라는 추정이 있다. secondary
뚫리는 방식
같은 USENIX 연구에서 bot은 85 ~ 100% 정확도로 대개 사람보다 빨리 풀었다. primary풀이 서비스의 공개 가격은 1,000건에 약 1 ~ 3달러다(Turnstile 1.45달러). 그 값이면 CAPTCHA는 벽이 아니라 수수료가 된다는 것이 리서치 파일의 추론이다. primaryETH Zurich의 2024년 모델은 reCAPTCHAv2 그림 문제를 100% 풀었다. secondary
우리 서버
못 함 페이지에 vendor의 스크립트를 넣고, 서버가 vendor의 검증 API를 불러야 한다. 서버 혼자서는 만들 수 없고, Verification client는 퍼즐을 풀지 못한다.

tarpit과 미끼 페이지

하는 것응답을 아주 천천히 흘려 연결을 붙잡는다.뚫리는 방식사이트당 깊이와 페이지 수를 제한한다.우리 서버만드는 중 Verdict tarpit은 있다. pool에서는 Worker를 붙잡는다.

자세히: 사례와 출처
판단
Nepenthes: 끝없이 생성되는 페이지마다 함정으로 돌아가는 링크가 수십 개 있고, 응답을 아주 천천히 흘려보내 연결을 붙잡는다. 페이지의 경고: "ANY SITE THIS SOFTWARE IS APPLIED TO WILL LIKELY DISAPPEAR FROM ALL SEARCH RESULTS" primaryiocaine: 요청마다 쓰레기를 줄지 시험을 줄지 분류 스크립트가 정한다. CPU와 메모리를 적게 쓰도록 만들었다. primaryCloudflare AI Labyrinth(2025-03-19): 사람이 보지 못하는 링크 뒤에 AI가 만든 미끼 페이지를 둔다. secondary
쓰는 곳
SourceHut이 2025년 3월 LLM 트래픽이 몰린 경로에 Nepenthes를 걸었다. "You may encounter certain pages which are not usable as a result." primary
사람이 치르는 값
분류가 틀리면 사람도 미로에 빠진다. 방어하는 쪽도 CPU와 검색 순위를 내준다.
뚫리는 방식
사이트당 깊이나 페이지 수에 한도를 두거나, CSS로 숨긴 링크와 nofollow 링크를 건너뛰거나, 질 낮은 문장을 알아본다.
우리 서버
만드는 중 rproxy에는 Verdict tarpit이 있다. 고르면 응답 없이 --tarpit S초(기본 10초) 동안 연결을 붙잡았다가 닫는다. 바이트를 천천히 흘리지 않고 그냥 기다리는 형태이고, 아직 verdict_decide()가 tarpit을 고르지 않는다. rproxy는 pool이라 걸린 연결 하나가 Worker 하나를 통째로 붙잡는다. 많이 고르면 방어가 스스로 만든 DoS가 된다. 연결 수천 개를 싸게 붙잡을 수 있는 것은 epoll뿐이다.

layer 5: 거래 바꾸기

질문을 "bot인가"에서 "누구이고, 누가 값을 내는가"로 바꾸는 layer다.

로그인, 유료 API, pay per crawl

보는 것계정, API key, 돈뚫리는 방식이름을 숨긴 crawler는 가격을 보지 않는다.우리 서버못 함 402는 쉽고, 결제는 CDN만 준다.

자세히: 사례와 출처
보는 것
계정이나 API key, 그리고 돈. pay per crawl은 확인된 crawler 신원(Web Bot Auth)과 결제 합의를 본다. 사이트는 crawler마다 허용, 요금, 차단 중 하나를 고른다. primary
쓰는 곳
Reddit(2023): 무료 한도를 넘으면 1,000 호출에 0.24달러. 월 약 70억 요청을 하던 Apollo 앱에는 연 약 2,000만 달러가 되어, Apollo는 2023-06-30에 문을 닫았다. secondaryX(2023): 무료 API는 쓰기 전용, Basic은 월 100달러에 읽기 10,000건 secondaryStack Overflow(2026): pay per crawl. "it's not a no, it's a yes if." 402를 보내기 시작하자 403 뒤에도 계속 오던 bot 일부가 멈췄다: "it's almost like they got the message." primary
사람이 치르는 값
계정이 없는 독자와 third-party 앱이 접근을 잃는다. Apollo는 접근성 때문에 쓰는 사람이 많았다. secondary
뚫리는 방식
값을 낼 수 있는 것은 자기를 밝힌 crawler뿐이다. 이름을 숨긴 crawler는 가격을 보지도 않는다. 그래서 이 layer는 아래 layer의 탐지가 있어야 선다.
우리 서버
못 함 402와 header를 보내는 것은 쉽다. 요금을 받으려면 확인된 신원과 결제 업체가 필요하고, 지금은 CDN만 그것을 준다.

Web Bot Auth

보는 것HTTP Message Signature(RFC 9421)뚫리는 방식서명하지 않는 bot에는 아무것도 하지 않는다.우리 서버가능, 아직 없음 OpenSSL에 Ed25519가 있다.

자세히: 사례와 출처
보는 것
HTTP Message Signature(RFC 9421) primary
왜 생겼나
IP 목록은 주소가 바뀌고 공유되면 깨지고, User-Agent는 "easily spoofed"이고, 사이트마다 bot마다 토큰을 나누는 방식은 너무 많다. primary
사람이 치르는 값
없음
뚫리는 방식
얌전한 bot이 누구인지 증명할 뿐, 서명하지 않기로 한 bot에는 아무것도 하지 않는다. 그런 bot에는 다른 layer가 여전히 필요하다.
우리 서버
가능, 아직 없음 OpenSSL이 들어와서 Ed25519 서명 검증은 할 수 있다. 서명하는 bot을 알아보는 길이 하나 생길 뿐이다. Verification client는 서명하지 않으므로 다른 검사를 대신하지 않는다. 실제로는 보통 CDN이 확인한다.

요청 하나 따라가기

가상의 서버 하나, crawler 넷
한 칸 오를 때마다 browser에 가까워짐

가상의 서버는 아래 다섯 검사를 이 순서로 한다. 네 crawler는 모두 robots.txt를 따르지 않는다. layer 1은 부탁이라서 막지 못한다. 검사 규칙은 설명을 위해 정한 가상의 설정이다.

  1. 검사 1. IP 블록리스트 (layer 3, accept 직후)

    A curl ✓ 통과 블록리스트에 없는 새 datacenter IP다. B User-Agent만 Chrome ✓ 통과 블록리스트에 없는 새 datacenter IP다. C 같은 handshake ✓ 통과 블록리스트에 없는 새 datacenter IP다. D headless browser ✓ 통과 residential proxy를 거친 집 IP다.

  2. 검사 2. User-Agent 표 (layer 2)

    A curl ✗ 403 User-Agent가 자기 도구 이름을 그대로 말한다. 가상의 표는 browser가 아니라고 밝힌 User-Agent를 막는다. B User-Agent만 Chrome ✓ 통과 User-Agent가 Chrome이라고 말한다. C 같은 handshake ✓ 통과 User-Agent가 Chrome이라고 말한다. D headless browser ✓ 통과 진짜 Chrome의 User-Agent다.

  3. 검사 3. JA4와 User-Agent 비교 (layer 2, TLS가 필요)

    A curl 검사 2에서 멈췄다. B User-Agent만 Chrome ✗ 403 User-Agent는 Chrome인데 JA4는 다른 TLS 라이브러리를 가리킨다. 말과 바이트가 어긋난다. C 같은 handshake ✓ 통과 browser의 TLS 라이브러리로 만든 handshake라 JA4도 Chrome이다. D headless browser ✓ 통과 진짜 Chrome이 보낸 바이트다.

  4. 검사 4. IP 평판과 rate limit (layer 3)

    A curl 검사 2에서 멈췄다. B User-Agent만 Chrome 검사 3에서 멈췄다. C 같은 handshake ✗ 429 datacenter IP 하나에서 요청이 몰린다. datacenter 평판과 IP당 한도에 둘 다 걸린다. D headless browser ✓ 통과 집 IP 수만 개에 나눠서 IP마다 요청이 몇 개뿐이다.

  5. 검사 5. proof of work (layer 4)

    A curl 검사 2에서 멈췄다. B User-Agent만 Chrome 검사 3에서 멈췄다. C 같은 handshake 검사 4에서 멈췄다. JavaScript가 없어서 여기 왔더라도 막혔을 것이다. D headless browser ✓ 통과, 200 JavaScript를 실행해 challenge를 푼다. 비용은 작다. 다섯 layer를 모두 넘었고, 그래서 layer 5가 생겼다: 이 crawler에게는 "bot인가"가 아니라 "누구이고, 누가 값을 내는가"를 물어야 한다.
