L3 HTTP ①: 양

rproxy 방어 layer L3, 약 10분 (읽기 포함)
목표: repeat가 10초에 200을 59번 받은 이유를 token bucket으로 말하기

1. 먼저 읽기

설명은 노트가 맡는다. 아래 두 절을 이 순서로 읽는다. 각 줄의 "볼 것"이 퀴즈에 나온다.

절볼 것
rproxy 요구분석 ④ HTTP: Request Verdict 카드rate limit이 규칙 표의 몇 번째이고, 무엇을 돌려주나
노트 03 rate limittoken bucket 그림, 열쇠, 뚫리는 방식, 사람이 치르는 값

L2의 마지막 질문에서 오라버니가 답했다: User-Agent와 TLS를 둘 다 Chrome으로 맞춘 crawler는 JA4로 못 잡는다. 그런 crawler에게도 남는 신호가 양과 행동이다. 이번에는 양을 본다.

2. 우리 bucket의 숫자

노트의 token bucket이 우리 코드에서는 숫자 다섯 개다.

이름어디뜻
ratestruct rate_limit_options1초마다 돌아오는 token 수 (--rate)
burststruct rate_limit_optionskey 하나가 가질 수 있는 token의 최대 (--burst). 새 key는 가득 찬 채로 시작한다
key_maxstruct rate_limit_options표에 둘 key 수. 차면 가장 오래 안 쓴 key를 잊는다
tokensstruct bucket그 key에 지금 남은 token. 소수일 수 있다
laststruct bucket그 key가 마지막으로 take한 시각 (초)

key는 기본이 client IP다 (--rate-key ip). rate_limit_take는 통과면 0을, 거절이면 다음 token까지의 초(최소 1)를 돌려준다. 이 값이 429의 Retry-After가 된다. 아래는 burst 3, rate 1일 때 key 하나의 시간 그림이다 (tests/test_rate_limit.c의 첫 테스트와 같은 숫자).

옆으로 밀어 보기 →

시각(초)  요청   take 전 tokens          돌려주는 값   take 뒤 tokens
0.0       1번    3 (새 key, 가득)        0  통과       2
0.0       2번    2                       0  통과       1
0.0       3번    1                       0  통과       0
0.0       4번    0                       1  거절 (429)  0
1.0       5번    0 + (1.0 - 0.0) × 1 = 1  0  통과       0

5번 줄을 본다. token을 채우는 timer는 따로 없다. take가 불릴 때 (now - last) × rate를 한 번에 더한다.

3. 예측: repeat는 200을 몇 번 받나

퀴즈 전에 숫자 두 개를 예측한다. 먼저 낱말:

  • Scene: bench/arena/scene.sh를 한 번 돌린 실험. rproxy와 Origin을 띄우고, Crawler script 하나와 사람 역할 human.py를 10초 동안 함께 보낸 뒤 상태 코드를 센다.
  • preset: Scene에서 rproxy에 주는 flag 묶음. none은 rate limit이 꺼진 묶음이다. layers는 방어를 모두 켠 묶음이고, rate limit은 --rate 5 --burst 10, key는 IP다.
  • repeat: 같은 2 MiB 파일 /bench/f019.txt를 쉬지 않고 받는 Crawler script. IP 하나(127.0.0.1)에서 4개 loop로 동시에 보낸다.

예측 하나: layers에서 10초 동안 repeat가 받은 200은 몇 개일까? 예측 둘: none에서 repeat는 10초에 요청 약 2,300개를 보냈다. layers에서 보낸 요청 수는 이보다 많을까, 적을까? 맨 아래 답안 칸에 숫자와 이유 한 줄씩 적는다. 정답은 6절에서 연다.

6. 예측의 답

예측을 적은 뒤 열기

하나: 200=59. 나머지 요청은 모두 429를 받았다. key가 IP라서 loop 4개가 bucket 하나를 나눠 쓴다. 처음에 burst 10개를 바로 쓰고, 그 뒤로는 1초에 5개씩 돌아온다. 10 + 5 × 10 = 60이 상한이다. 60번째 token은 첫 요청에서 정확히 10초 뒤에 돌아오는데, Scene은 그 전에 끝나서 59가 되었다. 출처: mini-webserver/docs/measurements/20261124-arena-layers.md의 "What limits each number".

둘: 더 많다. 2,280개에서 8,860개로 약 3.9배다. 429는 짧은 응답 한 줄이라 2 MiB를 받는 것보다 훨씬 빨리 끝나고, repeat는 기다리지 않고 바로 다음 요청을 보낸다. 그래서 Origin이 보낸 양은 4,564 MiB에서 8 MiB로 줄었지만, rproxy의 CPU는 1.3배로 늘었다. 요청마다 TLS handshake를 새로 하기 때문이다. rate limit은 비용을 없애지 않고 Origin에서 rproxy로 옮긴다. 출처: rproxy 측정 rate limit (Scene 3회의 중앙값).

이 옮긴 비용을 줄이는 법은 측정 노트의 "열린 질문"에 있다. 따라치기 뒤에 이야기해도 좋다.
