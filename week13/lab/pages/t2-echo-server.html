한 번에 한 client만 받는 echo 서버

C로 처음 손으로 친 서버 · client 둘, client 다섯을 붙여서 연결과 바이트가 어디서 기다리는지 확인

문제요약
client 둘 (06)Observed서버 앱이 client A를 상대하는 동안에도 커널은 client B와 연결을 맺고, B가 보낸 바이트를 Receive Buffer에 받아 둔다.Meaning서버 앱은 accept와 read를 부를 때가 되어서야 B의 연결과 바이트를 알게 된다.
Accept Queue가 차면 (06 과제)Observedbacklog를 1로 주면 Accept Queue에 연결 2개가 들어가고, 넘친 client의 SYN은 서버 커널이 답 없이 버려서 그 client는 약 2분 뒤 실패한다.Meaningbacklog는 값만큼 메모리를 미리 잡지 않으므로, 서버가 하나라면 크게 잡는다.

1. 앞 이야기와 용어

06 = lab에서 여섯 번째로 만든 실험 · 받은 바이트를 그대로 돌려주는 echo 서버를 손으로 침

06과 그 과제를 묶어 두 번째 트랙(T2)이라 부름. 앞 트랙(T1)에서 명령어로 본 socket → bind → listen → accept를 이번에는 C 코드로 직접 부름. 서버와 client는 모두 한 PC 안(localhost)에서 실행.

용어뜻
client서버에 연결한 클라이언트 · 여기서는 터미널의 nc localhost 8080 (nc = 연결해서 친 글자를 보내고 받은 글자를 보여 주는 명령) · 처음 붙은 client가 A, 다음이 B
listen, acceptlisten = 이 소켓으로 client를 받겠다고 커널에 알림 · accept = 커널이 맺어 둔 연결 하나를 꺼내 새 소켓 번호(fd)로 받음, 없으면 잠듦
Accept Queue커널이 연결을 맺어 놓고 프로그램이 accept로 꺼내 가기를 기다리는 줄
backloglisten의 둘째 인자 · Accept Queue의 길이 상한
Receive Buffer연결마다 커널이 받은 바이트를 프로그램이 read할 때까지 두는 곳
ss -tan커널이 가진 TCP 연결을 한 줄에 하나씩 보여 주는 명령 · 열 = 상태, Recv-Q, Send-Q, 내 주소:포트, 상대 주소:포트
Recv-Q, Send-Q줄의 상태마다 뜻이 다름 · LISTEN 줄: Recv-Q = Accept Queue에서 기다리는 연결 수, Send-Q = backlog · ESTAB 줄: Recv-Q = Receive Buffer에 쌓여 아직 안 읽은 바이트 수
LISTEN, ESTAB, SYN-SENTclient를 기다리는 소켓 · 맺어진 연결 · SYN을 보내고 답을 기다리는 client 쪽

2. client 둘 (06)

서버 프로그램이 A에 묶인 동안 B의 연결은 Accept Queue에서, B의 글자는 Receive Buffer에서 기다림

상황
서버 하나에 A가 붙어 대화 중 · 그 사이 B가 붙어 hello를 침 · 그다음 A를 Ctrl-C로 끊음
질문
서버 프로그램이 A만 상대하는 동안 B의 연결과 B가 보낸 글자는 어디에 있나
내 예측
① B의 연결은 맺어짐② B의 hello(줄바꿈 포함 6바이트)는 서버 커널 Receive Buffer에 쌓임 → Recv-Q 6③ A가 떠나면 B는 다시 치지 않아도 답을 받음
for (;;) {
    int conn_fd = accept(listen_fd, (struct sockaddr *)&addr, &addr_len);
    printf("accepted %s:%d\n", inet_ntoa(addr.sin_addr), ntohs(addr.sin_port));
    echo(conn_fd);        // 이 client가 떠날 때까지 여기서 안 돌아옴 → 다음 accept도 없음
    close(conn_fd);
    printf("closed\n");
}

while ((length = read(conn_fd, buffer, sizeof(buffer))) > 0) {
    write(conn_fd, buffer, length);
}                         // client가 떠나면 read가 0 → 반복 끝

B가 hello를 친 뒤의 ss -tan (주요 줄):

LISTEN  1   8   0.0.0.0:8080      0.0.0.0:*          # Accept Queue에 연결 1개(B), backlog 8
ESTAB   12  0   127.0.0.1:8080    127.0.0.1:40272    # 서버 쪽 B 연결, 안 읽은 12바이트
실제
① 맞음② 맞음, 12는 hello를 두 번 쳐서 6 × 2③ 맞음: A를 끊자 서버에 closed 다음 accepted 127.0.0.1:40272, B는 쳐 둔 hello 두 번의 답을 받음
이유
연결을 맺는 일은 커널이 혼자 함, 프로그램의 accept와 무관 · 글자도 커널이 먼저 받아 둠 · 프로그램은 accept, read를 부를 때 비로소 앎
웹 서버에서
이 모양 그대로면 client 하나가 오래 붙어 있을 때 다른 client 모두가 기다림 → 동시에 여럿을 받는 구조가 필요한 이유
전체 코드
06-echo/echo_server.c

3. Accept Queue가 차면 (06 과제)

backlog 1 → Accept Queue 자리 2칸 · 넘친 client의 SYN은 서버 커널이 답 없이 버림

상황
BACKLOG를 1로 바꾸고, A가 붙어 있는 동안 client 셋을 더 붙임
내 예측
① 셋째 client부터 막힘② 막힌 client는 서버 커널에게서 "Accept Queue에서 밀렸다"는 답을 받음
LISTEN    2  1   0.0.0.0:8080      0.0.0.0:*         # 기다리는 연결 2, backlog 1
ESTAB     0  0   127.0.0.1:8080    127.0.0.1:45404   # A, 서버 프로그램이 상대 중
ESTAB     12 0   127.0.0.1:8080    127.0.0.1:45416   # 둘째, Accept Queue
ESTAB     18 0   127.0.0.1:8080    127.0.0.1:34026   # 셋째, Accept Queue
SYN-SENT  0  1   127.0.0.1:34028   127.0.0.1:8080    # 넷째, client 쪽 줄만 있고 서버 쪽 줄은 없음
실제
① 틀림: 넷째부터 · 이 커널은 backlog보다 1칸 더 받음② 틀림: 서버 커널은 넷째의 SYN에 답하지 않고 버림 · 넷째 client 커널이 6번 다시 보내다(이 PC의 tcp_syn_retries = 6) 약 2분 뒤 포기, nc는 메시지 없이 끝남
비교
아무도 듣지 않는 포트에 연결하면 서버 커널이 RST를 바로 돌려보내 3ms 만에 실패 · Accept Queue가 찬 서버는 답이 없어 2분
웹 서버에서
backlog는 프로그램이 잠깐 밀릴 때 client를 붙잡아 두는 완충 · 값만큼 미리 잡는 메모리는 없고 실제로 기다리는 연결만큼만 씀, 상한은 somaxconn(이 PC 4096) → 서버가 하나면 크게 · 작게 잡을 이유는 client가 옮겨 갈 다른 서버가 있을 때뿐
