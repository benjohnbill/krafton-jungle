rproxy 요구분석: 단계마다 무엇을 보고 누구를 거르나

앞 단계일수록 서버 비용은 작지만 보이는 신호가 적음
뒤 단계일수록 신호는 많지만 그곳까지 오는 데 비용이 쌓임

1. 목표: 방어의 가성비

이득 없는 crawler 부하 → 요청이 단계를 지날수록 비용이 쌓임 → 앞 단계에서, 적은 신호로 거름

방어 하나가 남는 장사이려면어기면
방어 비용 < 그 방어가 아끼는 서빙 비용막는 편이 그냥 보내는 편보다 비싸다
방어 비용 < crawler가 그 방어를 피해 가는 비용군비 경쟁에서 서버가 먼저 지친다 (02 역사)

2. 사용자: 운영자가 가르는 client 셋

막을 대상만이 아니라 잘못 막으면 안 되는 대상도 요구

사용자운영자가 원하는 것잘못 판단하면
진짜 사용자막지 않기. 느려지지 않기오탐: 사람이 막히거나 기다린다
나쁜 crawler싸게, 앞 단계에서 거르기미탐: Origin의 CPU와 대역폭이 샌다
착한 bot신원이 확인되면 통과시키거나 값을 받기검색 노출이나 거래를 잃는다

단계 하나 = 카드 하나

거르는 기준

4. 특이사항: 측정 요약

그림과 근거는 rproxy 측정 노트

방어한 줄
rate limitOrigin MiB는 1/59 ~ 1/588로 줄지만, rproxy CPU는 1.3 ~ 3배로 늘어남
dropTLS 서명 전에 끝나서 rproxy CPU까지 줄어듦 (spread 15.6 → 11.1 s)
tarpitcrawler의 발을 묶어 rproxy CPU 4.9 → 0.09 s, Origin MiB 0
사용자진짜 사용자는 p95 그대로(오탐 없음). 착한 bot은 의도대로 통과

5. Not-Goal

하지 않는 것이유
완벽한 차단막는 비용이 아끼는 비용보다 커지는 지점부터는 손해
CAPTCHA사람이 풀어야 해서 Scene이 잴 수 없음. 진짜 사용자의 비용도 큼
reverse DNS착한 bot의 신원 증명은 Web Bot Auth가 맡음
JS를 돌리는 browser 판별rproxy는 HTML을 고치지 않음. 그 군비 경쟁은 crawler가 앞섬 (02 역사 라운드 6 ~ 9)
대량 트래픽 공격 (DDoS)kernel과 망 장비의 일. rproxy는 연결이 생긴 뒤부터 봄
HTTP/3 (QUIC)rproxy는 TCP 위의 HTTP/1.1만 받음

agent 제안 CAPTCHA와 reverse DNS는 SPEC §11 v2가 뺐고, 나머지 넷은 agent 제안이다.
