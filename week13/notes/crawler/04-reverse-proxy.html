우리 Reverse Proxy의 방어 layer와 경기장

03의 layer 여덟 개가 rproxy의 어느 단계, 어느 module에 있는지
Crawler script 10개로 잰 Origin의 부하와 방어의 대가

주제요약
연결 하나의 길Observedrproxy는 Verdict를 두 번 정한다: TLS handshake 전의 Connection Verdict와 request parse 뒤의 Request Verdict다.Meaninghandshake 전에 drop한 연결은 RSA 서명도, Origin의 일도 만들지 않는다.
경기장Observedlayers preset에서 Origin이 보낸 바이트가 repeat는 4896.3 MiB에서 8.0 MiB로, disguised는 275.4 MiB에서 0으로 줄었다.MeaningCrawler script 10개 중 polite와 signed는 통과했고, 나머지 여덟은 각자 다른 layer에서 멈추거나 느려졌다.
대가와 한계Observedtarpit이 Worker를 모두 붙잡아서, disguised 옆에서 돈 human.py는 10초 동안 응답을 하나도 받지 못했다.Meaningcrawler를 붙잡는 방어는 서버의 자원도 붙잡으므로, 사람의 요청까지 멈출 수 있다.

이 노트는 리서치 파일이 아니라 mini-webserver CJG 브랜치의 commit f9dda4d에 있는 SPEC, ADR, 코드, 측정 파일을 보고 썼다. 숫자는 모두 그 파일에서 가져왔고, 출처 칩(primary)은 그 파일로 간다. 추론한 문장은 추론이라고 적었다.

1. 자리: client와 Origin 사이

  • rproxy는 Origin(server) 앞에서 따로 도는 프로세스다. server 안의 Route로 두면 검사가 Origin과 같은 Worker를 쓰고, Origin이 proxy 뒤에 숨을 수 없다. primary
  • OpenSSL은 rproxy만 링크한다. TLS handshake, 암호화, SHA-256, Ed25519는 OpenSSL이 하고, ClientHello parse와 JA4 계산은 우리 코드가 한다. primary
  • Origin으로 가는 요청에는 X-Forwarded-For(client IP)와 X-JA4가 붙는다. rproxy는 parse한 필드로 요청을 새로 쓰므로, 그 밖의 header는 Origin에 가지 않는다.
  • --origin을 여러 번(최대 8) 주면 Origin들이 차례로 요청을 받는다(Round-Robin). 연결이 실패하면 다음 Origin을 한 번 더 시도하고, 그것도 실패하면 502다.

2. 연결 하나의 길

단계언제보는 것Verdict
Connection VerdictClientHello를 엿본 뒤, TLS handshake 전client IPJA4Block tablepassdrop (응답 없이 닫음)tarpit
Request Verdictrequest parse 뒤위의 셋User-Agent, targetrate limit, Behavior counterProof of work 풀이, bot 서명passdeny (403), slow (429)tarpitchallenge (401), pay (402)

handshake 전에는 HTTP가 없어서, Connection Verdict는 닫거나 붙잡는 것만 할 수 있다. 대신 drop한 연결에는 RSA-2048 서명이 없다. 측정에서 rproxy는 요청 하나에 CPU 2.1 ms를 썼고, 그중 0.9 ms가 이 서명이다. primary

drop은 ClientHello를 읽지 않은 채 socket을 닫는다. 그러면 kernel이 RST를 보내고, TLS 바이트는 하나도 나가지 않는다. nginx의 return 444와 ssl_reject_handshake on을 본뜬 것이다. Connection Verdict의 tarpit은 Verdict 종류로만 있고, 아직 그 Verdict를 고르는 규칙이 없다.

Request Verdict가 request 뒤에 오는 이유는 둘이다. User-Agent와 target은 request 안에 있고, 403과 429는 HTTP 응답이다.

4. Request Verdict 규칙 순서

verdict.c의 rules[] 표를 위에서부터 보고, 처음 맞는 규칙이 Verdict를 정한다. 맞는 규칙이 없으면 pass다. primary

  • client를 Block table에 넣는 두 규칙(Honeypot, scanner)이 맨 앞이다. 가장 강한 증거이고, 이름을 밝히고도 robots.txt를 무시하는 crawler도 잡으려는 것이다. 그래서 서명한 bot도 이 둘은 건너뛰지 못한다.
  • pay가 crawler 이름보다 앞이라서, pay 대상 경로에서는 403 대신 402가 나간다.
  • false browser는 JA4 table이 아는 JA4만 본다. 표에 없는 JA4는 증거로 치지 않아서, 표가 모르는 진짜 browser는 통과한다.

5. 경기장: Crawler script 10개

bench/arena/scene.sh <crawler> none layers는 Crawler script 하나와 human.py를 나란히, preset마다 10초씩 돌린다. Origin은 ./server --model pool --delay 10이다. Scene은 재기만 하고, 합격과 불합격을 가리지 않는다. primary

자세히: 두 preset의 flag

none: flag 없음. 그래도 robots.txt, Honeypot, User-Agent 규칙, scanner 규칙은 켜져 있다. 그래서 named, spread, signed는 none에서도 403을 받았고, trapped는 none에서도 drop됐다.

layers: 모든 방어를 켠다.

000은 응답이 없었다는 뜻이다. Origin이 보낸 MiB가 가장 크게 준 넷은 아래와 같다. 눈금은 로그다.

  • 10초에 약 59번 통과(repeat, longtail, revalidate, solver): token bucket이 처음에 10개를 주고, 그다음 초당 5개를 채운다. 10 + 5 × 10 = 60이다. rate limit의 열쇠는 IP이고, 이 넷은 IP 하나에서 보낸다.
  • repeat와 revalidate는 59번 통과했지만, Origin에 간 요청은 4번뿐이고 나머지 55번은 cache가 답했다. revalidate는 그 55번을 304로 받았다. 8.0 MiB는 2 MiB 파일 4번으로 보인다(추론).
  • signed는 named와 User-Agent(GPTBot/1.1)가 같다. 다른 것은 서명 하나이고, named는 402를, signed는 200을 받았다. Origin은 16.6 MiB를 보냈다. dataset이 16.7 MiB이고, 나머지 요청 2176개는 cache가 답했다.
  • spread의 주소 32개 중 Block list(127.0.0.16/28)에 든 16개는 handshake 전에 drop됐고(000), 나머지 16개는 402를 받았다.
  • trapped는 /trap/을 한 번 요청한 뒤 IP가 Block table에 들어갔고, 그 뒤 10초 동안 연결 6860개가 handshake 전에 drop됐다.

6. 대가와 한계

disguised는 Chrome User-Agent에 curl의 JA4를 보내므로, 요청마다 tarpit을 받는다. tarpit은 Worker 하나를 --tarpit 초(기본 10초) 동안 sleep으로 붙잡은 뒤 응답 없이 닫는다. rproxy의 Worker는 기본 4개이고, disguised는 loop 8개로 보낸다. Worker가 모두 묶이자 human.py는 대기열에서 10초를 기다렸고, 두 client 모두 응답을 하나도 받지 못했다. primary

계획, 아직 없음 Worker를 붙잡지 않는 tarpit(event loop의 timer)이나 drop으로 바꾸면 이 대가가 사라진다고 측정 파일은 적었다. 아직 재지 않았다.

rproxy는 응답 하나를 보내고 연결을 닫으므로, 요청마다 TLS handshake를 한다. parity 측정에서 rproxy는 요청 하나에 CPU 2.1 ms를 썼고, 평문 HTTP와 keep-alive를 쓰던 Proxy Route는 0.08 ms를 썼다. 약 25배다. primary

계획, 아직 없음 rproxy의 keep-alive나 TLS session resumption이 있으면 handshake가 아니라 cache를 잴 수 있다고 측정 파일은 적었다. 아직 재지 않았다.

이 경기장의 한계:

  • curl로 만든 Crawler script는 모두 JA4 하나를 같이 쓴다. 그래서 Honeypot hit는 JA4가 아니라 IP만 Block table에 넣고, layers의 rate limit 열쇠도 IP다.
  • human.py는 Python urllib이고 TLS는 OpenSSL이다. 진짜 Chrome(BoringSSL)이 아니라 browser의 대역이고, JA4 table이 그 JA4를 browser라고 부를 뿐이다.
  • localhost에서 돌렸으므로, CIDR range 127.0.0.16/28이 hosting 회사의 ASN 목록을 대신한다.
  • rproxy에는 keep-alive가 없다. 연결 하나에 요청 하나이다.
  • 각 Scene은 preset마다 10초씩 한 번 돌린 값이다.
