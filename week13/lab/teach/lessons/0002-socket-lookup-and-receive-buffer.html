0. L1 복습

답을 먼저 말하고 연다. 대기열에 쌓이는 것은 무엇이고, fd는 언제 생기나?

답 열기

대기열에는 handshake가 끝난 연결이 쌓인다. fd는 accept가 그 연결을 꺼낼 때 만든다. 연결은 close까지 이어지고, 그동안 같은 conn_fd로 read와 write를 몇 번이든 한다.

L1에서 오라버니가 붙인 tcpdump 줄이 이번 lesson의 출발점이다. 그때 서버 앱은 accept조차 부르지 않았다.

127.0.0.1.8080 > 127.0.0.1.49954: Flags [.], ack 67, ..., length 0

퀴즈 1번이 이 줄을 묻는다. 아래를 읽기 전에 먼저 골라도 된다.

1. 커널은 주소 네 개로 소켓을 찾는다

서버가 커널에 부탁하는 순서 §3에서 포트 8080에 소켓이 둘 있었다: LISTEN 줄(상대 *)과 ESTAB 줄(상대 127.0.0.1:48196). 패킷이 도착하면 서버 커널은 둘 중 하나를 골라야 한다.

한 문장. 커널은 먼저 주소 네 개(상대 IP, 상대 포트, 내 IP, 내 포트)가 모두 맞는 연결 소켓을 찾고, 없을 때만 내 포트가 맞는 listen 소켓으로 보낸다.

근거: Linux 커널 inet_hashtables.h의 __inet_lookup은 __inet_lookup_established(net, saddr, sport, daddr, hnum, ...)를 먼저 부르고, 결과가 없으면 __inet_lookup_listener를 부른다.

2. ACK는 "커널이 받았다"는 뜻이다

한 문장. 데이터가 오면 서버 커널은 그 소켓의 수신 버퍼에 넣고 바로 ACK를 보낸다. 서버 앱의 read는 나중에 수신 버퍼에서 바이트를 꺼내 갈 뿐이다.
write("hello\n"), 클라 커널의 송신 버퍼로 데이터 6바이트 ACK. 바이트는 서버 커널의 수신 버퍼에 있음 (앱은 아직 모름) read(), 수신 버퍼에서 꺼내 앱 메모리로. 이때 비로소 앱이 앎

tcp(7)은 이 버퍼를 "The socket receive buffer space is shared between the application and kernel."이라고 쓰고, 아직 안 읽은 양을 "the amount of queued unread data in the receive buffer"라고 부른다 (tcp(7), SIOCINQ). 버퍼 크기의 상한은 SO_RCVBUF다: "Sets or gets the maximum socket receive buffer in bytes." (socket(7))

3. ss의 두 열, 연결 소켓에서

L1에서 LISTEN 줄의 Recv-Q는 대기열의 연결 수였다. 연결 소켓(ESTAB)에서는 바이트 수다. 커널 tcp_diag.c:

열커널 계산뜻
Recv-Qrcv_nxt - copied_seq커널이 받았지만 앱이 아직 read하지 않은 바이트
Send-Qwrite_seq - snd_una앱이 write했지만 상대 커널이 아직 ACK하지 않은 바이트

4. 직접 본다 (퀴즈 4–5번을 먼저 고르고)

tools/no_read.py는 accept를 한 번 하고 read는 부르지 않는다. week13/lab/teach/에서:

# 터미널 1: read 안 하는 서버
python3 tools/no_read.py

# 터미널 2 (선택, sudo): 데이터와 ACK 보기. 터미널 3보다 먼저 켠다
sudo tcpdump -i lo -n port 8080

# 터미널 3: 클라이언트. hello 를 치고 엔터
nc localhost 8080

# 터미널 4: 연결 소켓의 두 열
ss -tan 'sport = :8080 or dport = :8080'

출력을 세션에 붙여 넣는다. 그다음 터미널 3에서 몇 줄 더 치고 ss를 다시 본다. 어느 줄의 어느 숫자가 커지는지 본다.
